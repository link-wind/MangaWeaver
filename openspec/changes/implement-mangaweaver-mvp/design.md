## Context

项目目前只有目标与架构文档，没有业务代码。动机与范围见 `proposal.md`；目录以 `docs/ARCHITECTURE_DRAFT.md` 第 13 节及用户最终选择为准，早期 Draw.io 图不是当前结构依据。

这次是跨预处理、规划、视觉条件与视频生成的首次实现，需要明确多对多来源关系与 H3 能力边界，因此保留设计文档。首版以用户选定的一场短戏为输入，不自动拆整章。

## Goals / Non-Goals

**Goals:**
- 按已选包结构迁入参考项目有效实现，建立可独立调用的三阶段命令。
- 用明确的源格、镜头、关键帧和生成段身份承载镜头编排与节奏设计。
- 增加分类与编排、动作镜头演出两组 Creator／Reviewer，并接回参考项目的反馈迭代方式。
- 形成静态首帧、动作首尾帧的真实任务映射；能力不符时明确停止，不做伪支持。

**Non-Goals:**
- 无全局自主导演、Agent 类框架、插件注册、Web／数据库、自动依赖图或通用容错系统。
- 无细粒度人体运动求解、历史视频续写、latent prefix、模型训练或独立完整声音制作系统；使用并保留视频生成器的原生声音。
- 规范中的场景是验收依据，不要求为每条场景建立独立自动测试。

## Decisions

### 1. 先核实参考版本与 MiniMax H3 接入能力

实施第一步记录参考仓库提交、相关文件与复用许可信息，阅读原有调用和提示词，再迁移实际需要的代码。原项目的 H3 路线是整张分镜参考，不能从它已有的后端名称推导首尾帧能力。

先核实拟用 H3 官方／实际可用入口的首帧与首尾帧参数、时长范围、响应、任务查询及下载行为，记录到简短接入说明。文档和代码核查不提交视频；实际生成在配置可用时用最小样例验证。

若没有可核实的首尾帧接口，保留模型选择与既定目标，完成能独立推进的本地和第二阶段工作，将相关视频任务保持未完成并说明缺口。此时不实现“多参考图等于首尾帧”的替代路线；若需修改方案，先回到用户讨论。该能力核实是明确的实施关口，不是已验证可用的功能承诺。

备选的自动换模型、退回整段参考和假接口占位均不采用，避免偏离用户已选模型或虚报端到端完成。

### 2. 采用薄入口和直接模块调用

使用 `pyproject.toml` 定义本地包与 `mangaweaver` 命令。`cli.py` 以简单参数解析提供 `preprocess`、`plan`、`generate` 阶段入口；不保留旧脚本兼容层。

`config.py` 读取 `.env`、命令参数及运行路径，显式传给阶段函数；`io.py` 仅封装实际复用的读写；`clients/gemini.py` 和 `clients/minimax.py` 直接承载所需模型调用。不建设客户端基类、服务层或注册表。

包内模板以可随安装定位的资源方式包含，源文件仍按用户选定的根目录 `prompts/` 分组，避免命令仅在仓库根目录可用。具体打包映射在建立 `pyproject.toml` 时一并处理，不复制两套模板。

相对保留平铺目录，这一选择是用户已确认的工程组织调整；函数和行为仍优先参考原实现，不借迁移重写流程。

### 3. 来源记录与输出镜头分离

`schemas.py` 集中定义必要 JSON 结构与字段、引用关系校验，不引入通用实体系统。

| 数据 | 核心字段 |
| --- | --- |
| 来源记录 | `case_id`、`panel_id`、`page_id`、顺序、图像、对白、角色、事件、事实与推断 |
| 镜头清单 | `shot_id`、顺序、`source_panel_ids`、事件关联、`type`、表达目的、景别、时长、编排理由、`cut` 衔接 |
| 动作演出 | `shot_id`、入点／出点、节拍、原漫画瞬间的阶段与位置、有序锚点及秒数 |
| 视觉素材 | `keyframe_id`、`shot_id`、锚点角色、图像、来源依据、对应方案版本 |
| 生成任务 | `segment_id`、`shot_id`、模式、首帧／尾帧、目标及请求时长、提示、模型、任务 ID |
| 评审结果 | 选择、可采用状态、问题位置、证据、修订对象、建议、不确定项 |

跨格动作可以合成一个镜头，一格也可以支持多个镜头。来源脚本仍可逐格组织，最终视频不再靠源格编号或列表位置匹配。以显式引用代替原有一格一片段假设。

### 4. 编排与动作镜头演出分层

`planning/script.py`、`script_review.py` 迁入原作脚本与审查逻辑，尽量保留人物、对白和来源检查。

`shot_arrangement.py` 结合完整场景识别事件，分类并编排镜头。分类取决于呈现是否依赖主要状态的变化，而非是否有眨眼、口型或运镜；选择完整场景方案，不从不同候选任意拼接时序结构。允许合并、拆分和有依据的过渡／反应镜头，不改变原作关键事件与因果。

`shot_direction.py` 仅对动作镜头细化入点、关键瞬间时间位置、强调、停顿和出点。静态镜头跳过该步骤。它不使用固定的准备—执行—反应模板强迫所有动作展开。

两组对应 Reviewer 检查来源覆盖、类型、镜头关系与节奏；用户后续要求控制生成数量，当前所有环节默认只生成一个候选，Reviewer 仍判断可用性；规划最多两轮，按明确反馈修订必要内容。候选数仍可配置，不固定每页镜头或关键帧数量。

### 5. 视觉产物按生成用途改变，原作约束不丢失

`storyboard.py` 与 `storyboard_review.py` 复用原图像生成和比较调用，但调整原提示词的严格一格一镜头、姿态和布局匹配要求。

- 静态镜头：生成一张选定分镜，用作视频首帧。
- 动作镜头：按选定锚点生成必要关键画面，保持同一连续镜头的空间和机位可解释，原漫画画面可位于中段或末段。
- 原作人物、事件、关键关系仍须保留；因授权机位或时间变化导致的构图差异按演出计划评审，不机械判错。

关键画面制作时传入相关漫画、角色参考及已选必要画面，检查系列一致性。选定图必须绑定产生它的脚本与演出版本；保留旧候选时不得混用新计划。

### 6. 第二阶段用有限轮次汇总反馈，不引入自由路由框架

`planning/pipeline.py` 按来源脚本、编排、动作演出、视觉分镜顺序执行，收集本轮评审后，在下一轮按明确归属修订。编排问题回编排，演出问题回演出，图像未落实设计回分镜；上游事实问题回脚本。

只对修订内容及需要更新的下游显式重跑，保留正确结果；首版用运行目录和显式阶段参数完成，不实现自动依赖传播。阻断问题仍存在时停止并保留报告，不以候选中最好代替通过。

### 7. 第三阶段分清任务构建、调用、评审和剪辑

用户后续指定视频生成统一使用 `MiniMax-H3-Lite`，默认 `480P`；先前标准 H3 的单段验证保留历史模型信息，不作为 Lite 的实测结果。

`generation/tasks.py` 接收选定镜头与实际图像：静态镜头生成一项首帧请求；动作镜头按 K0→K1、K1→K2 构建独立首尾帧请求。不把不同镜头间的 `cut` 编译成连续插值。

`generation/pipeline.py` 使用 MiniMax 客户端提交、查询、下载并保存任务 ID，复用参考项目的候选选择思路。时长不符时提交前报出计划与能力差异，不自动拉长、加速或改变关键瞬间位置。

`video_review.py` 保留参考项目视频比较逻辑，检查各段及完整镜头的端点、接缝、节奏和与相邻镜头的关系；首版不自动触发全局上游重规划。

`assembly.py` 按镜头顺序连接，检查必要素材完整和导出视频可读；只去除确认重复的接缝帧。交付有声版并保留原始音轨，首版输出固定为 720P、24 fps，与 H3 帧率保持一致。原生 480P 输出在导出时统一尺寸，放大不代表细节恢复。

### 8. 参考模块迁入对应职责，不额外建立基础设施

| 参考位置 | 迁入位置／修改 |
| --- | --- |
| `croppanels.py`、`magi.py`、角色描述生成 | `preprocessing/`，保留已有算法与调用方式 |
| 脚本、分镜生成与评审模块 | `planning/` 对应模块，扩展镜头映射与演出输入 |
| `run_all.py` | `planning/pipeline.py`，增加编排和演出，不加入自主导演 |
| `utils.py` 中 Gemini 调用 | `clients/gemini.py`，保留有效请求与必要有限重试 |
| `video_models.py` 中 H3 调用与任务处理 | `clients/minimax.py`，先核实入口能力再扩展参数 |
| `create_video.py` | `generation/`，按已选职责拆分，不迁入无关模型实现 |
| 运行目录、日志、配置记录 | `config.py`、`io.py` 及阶段调用处，保留直接实现 |

保留原代码和提示词的来源记录；未用到的自部署模型与完整评测工具不迁入主运行环境。

## Risks / Trade-offs

- [H3 入口不能表达目标条件] → 首批核实并记录能力，相关任务不虚报完成；继续独立上游工作，不自动换模型。
- [首尾端点近似但运动接缝不连续] → 在完整镜头上评审并保留问题，不增加未经验证的自动修复链。
- [模型时长粒度限制镜头节奏] → 显式检查目标与请求时长，报告不适配供调整，不静默变速。
- [编排合并丢失原作信息] → 对来源覆盖和关键事件进行明确审查，保留多对多映射与依据。
- [同一模型生成和审查存在偏差] → 最小样例由人工检查原作对应与视频结果，审查输出不作为效果保证。
- [目录调整引入导入和资源路径问题] → 用安装后 CLI 帮助、一次非根目录模板读取和最小本地链路验证，不扩展大量兼容测试。

## Migration Plan

项目尚无业务代码，无生产数据迁移。先记录参考版本和 H3 能力，再建立可安装骨架；按预处理、第二阶段、视频任务和剪辑依次迁入与实现。先以已有有序漫画格打通第二阶段，避免预处理模型资源阻塞规划开发。

每阶段提交可检查的 JSON、图像或视频，不用空模块和 Mock 成片代表完成。失败保留本次运行目录，可显式指定阶段重跑；不建设额外部署与回滚框架。

### Gemini 3.8 Flash 实测追加

用户指定规划及评审为 gemini-3.8-flash，生图保持 GPT Image。该渠道原生 response_schema 可能被忽略，因此沿用 Kie 已有的 JSON Schema 提示约束与本地 Pydantic 校验，只去除完整 Markdown 包装，不修补 JSON。结构错误保存原始文本，失败不冒充通过。实际出现初稿漏掉前景拳头且 Reviewer 拒绝的案例，因此规划在脚本审查未通过时先反馈到下一轮，不进入编排与生图；沿用现有两轮上限和运行目录，恢复时重新读取该轮缓存即可，不建设新状态系统。


### 真实链路反馈修正

规划增加本地 PlanningDraft（只存已有阶段数据结构），用于未通过阶段的显式恢复，不对视频生成暴露。脚本、编排、动作演出全部通过才生图；单张图未通过即停止该序列，不把它作为后续参考。已通过的同版本锚点前缀可以保留，只对实际阻断反馈修订，accepted=true 的提醒不自动触发重绘。草案仍走固定顺序、每次最多两轮的 Creator／Reviewer；没有新增服务、路由框架或供应商回退。

真实样例暴露了上下文缺口：direction_review 原先只有原图与候选，漏传了已通过的来源脚本；现传入对应格的 verified_panel_facts 与 source_image_order，并要求复核遮挡人物。生图输入按当前镜头过滤人物，演出上下文移除其他 anchors，只强调本张锚点及与前序画面的风格连续性。


视频审查显式标注原漫画参考、端点图、前一视频和本次候选，并传入对应已审查事实，避免把参考漫画文字认成视频字幕。首次审查和复核均保留。实际视频质量失败时可以提供标注为未通过的完整测试预览，不能发布为通过验收的 final.mp4。

生成阶段仅对同宽且高度恰差1像素的端点，复制较小图底部一行保存派生图与来源记录；原评审图和哈希不变。不是自动裁切／缩放修复叙事或替代重画，其他尺寸差继续报错。

### 彩色动画目标修正（2026-10-24）

用户确认输出为彩色二维动画。删除关键帧“前序黑白则继续黑白”的限制，保留造型与剧情而非黑白渲染。沿用现有 Character.description 存放已确认配色，未知颜色标明改编选择；不增加配色 Agent 或额外生图阶段。来源脚本 Creator／Character Reviewer 确认配色后，将同一角色描述传给关键帧 Creator 和单图／序列 Reviewer；视频请求与评审要求持续彩色并检查变色闪烁。旧黑白运行保持历史状态，不能因提示词修改改标为彩色合格；彩色重生成须显式运行新的素材制作与评审。

### 原生声音恢复（2026-10-24）
