动机和范围见 [proposal.md](proposal.md)。本次跨输入区、桌面协议、任务收件、专业委派和时间线，但继续使用单项目文件式执行，不改变三阶段制作机制。

当前实现的具体接入点：

- `desktop/src/App.tsx::messageAgent()` 在 `busy` 时无条件调用 `submit_revision`，没有选中节点还会默认 `arrangement`。
- `agent/tasks.py::submit()` 已提供短锁收件、版本和授权快照、撤回；`workflow.py::consume_revision()` 已提供认领、冲突检查、修订运行及恢复。这些保留为真实内容修改的执行路径。
- `workflow.py::stage_tool()` 和 `events.py::professional_call()` 已记录阶段任务及真实 Creator／Reviewer 调用；任务书和回报补在这些边界，不建立另一套执行器。
- `AgentContext` 当前仅有选中 ID 与节点摘要；`CreativeComposer`、`CreativeTimeline` 和现有画布完成回执可承载引用与交接展示。
- 前一变更 `unify-agent-task-workflow` 已实现但尚未归档，本次收窄其“运行中待修改”语义，其余授权、版本、有限修订和显式恢复约定保留。

## Goals / Non-Goals

**Goals:**

- 让一条消息具有固定归属和清楚的实际处理结果，问答、修改、后续工作各走正确路径。
- 将真实对象与版本引用送到专业模型输入，而不止显示标签。
- 用少量结构化字段连接总 Agent、阶段 Creator／Reviewer 和实际产物，复用现有任务状态与事件。

**Non-Goals:**

- 不新增 HTTP 服务、数据库、Agent SDK、通用消息总线、任意递归委派、并行制作或自动依赖传播。
- 不建设完整 `@` 搜索、跨项目素材索引、共享角色／场景库、候选采用切换。
- 不改变镜头编排算法、彩色与声音目标、模型配置或视频路线。H3 能力校验保持原状，不能将媒体引用等同于任意参考／首尾帧能力；Lite／480P 实测不属于本轮任务。

## Decisions

### 1. 扩展现有消息收件，不把所有消息变成修订

在现有 schema 和 TypeScript 类型中增加精简的消息封套；`pending_requests/` 继续作为唯一待处理收件位置。

| 字段组 | 语义 |
| --- | --- |
| `id`、原文、时间 | 一条用户要求的稳定身份，也作为时间线去重依据 |
| `delivery` | `steer` 调整当前任务，或 `follow_up` 稍后处理；它说明何时、交给谁，不表示一定要修改内容 |
| `intent` | 待理解、问答、内容修改、制作请求、执行控制；原文保留，理解结果有据可查 |
| 归属 | 项目、来源请求、当前任务关联、页面和运行基线；后续要求的最终任务身份单独保存 |
| 范围 | 目标、明确引用、用户授权快照、终点与必要约束 |
| 处理回执 | 沿用收件状态并补充答案／结果、实际接收任务和产物；不另建工作流状态体系 |

运行期间输入区默认 `steer`，仅提供“调整当前任务／稍后处理”的小菜单；普通问答仍可直接输入。空闲发送沿用现有总 Agent 入口。发送完成后保留固定引用与归属，清空草稿；界面不能用最新选中状态重新解释旧消息。

桌面新增统一消息收件命令，保留旧 `submit_revision` 数据的读取和恢复入口。旧记录缺少新字段时按原有内容修改理解，不做模型补分类、不自动执行。只在真正修改分支调用原 `consume_revision`；去掉前端无目标时默认编排的行为。

选择这一方式而非新增消息服务，是因为现有原子收件和任务账本已具备并行 UI 收件、串行引擎处理的边界。

### 2. 本地控制与只读回答优先，模型理解放在安全边界

处理顺序如下：

1. 停止按钮和独立明确停止指令（如单独“停止”）直接复用现有 `interrupt_workflow` 与进程停止路径；不等待长模型调用、不排为修订。不用长文本子串匹配识别停止，带条件或否定的复杂表达由总 Agent 理解。
2. 明确的进度查询从任务快照读出角色、阶段、真实状态和已有产物。少量精确表达可映射本地查询，其余自然语言由边界处总 Agent 判断；不为此搭建关键词分类体系。确定性的进度回答不调用生产模型、不写父任务终态。
3. 其他消息先保存待处理。当前模型调用完成并保存检查点后，固定总 Agent 在已有结构化动作中理解意图与目标；所需模型调用计入已有有限决策预算。对普通问题只开放读取／回答，不开放制作工具，回答后返回原任务，不新开第二套对话执行器。
4. 确认是内容修改才进入原版本检查、修订运行、专业审查路径。修改通过后沿用“检查新版本、继续原制作”的既有暂停点，不静默追加生成。
5. 当前任务补充不能悄悄变成另一页的新制作；目标或范围不匹配时请求明确决定，并保留原任务及消息。

只读进度收件和撤回使用现有短锁，不能争抢整段制作锁。活动引擎仍是 `session.json` 和制作任务的主写入者；运行中即时回答写在对应收件回执，由时间线按消息 ID 合并，主引擎在检查点接回会话，避免两个进程同时覆写完整会话。停止相关写入继续沿用既有中断通道。

不选择所有输入立即另起总 Agent 调用，避免两套执行同时修改页面与会话；也不继续将所有输入排为修订，避免问答触发付费工作。

### 3. 当前补充与后续要求使用不同消费时机

- `steer` 在检查点前后核对固定任务、内容修订号与目标引用；单纯新增产物或进度不能被误判为用户内容版本变化。只暂停受影响的下一项工作，不改写正在进行的调用输入。
- 若修订中的临时脚本检查点尚未发布镜头，使用任务书绑定且签名未变化的输入计划解析原镜头；确实需要从该输入计划修订时保存明确基线，再沿原 fork 路径创建新运行。临时产物仍保留，输入基线缺失或变化则报错，不把残缺草案当作完整计划。
- `follow_up` 不触发当前任务的修订检查点中断。只有当前父任务正常完成后，活动客户端才串行接收下一条；失败、等待用户、中断及停止都不自动出队。
- 后续要求被接收时生成独立任务，先保存 `origin_request_id` 与关联身份再执行；不能因同一运行目录被 `root()` 复用而覆盖前任务目标。排队时的来源任务关联与执行时的独立任务身份分开记录。
- 自动推进仅限用户已明确指定的目标和授权。例如“这页编排完成后规划下一页”且两页规划已授权可以连续完成；新生图／新视频、未选页或目标不清则沿原授权／提问流程等待。
- 以接收时间及稳定 ID 确定顺序。尚未接收可撤回；同一 ID 再递送返回原回执。已认领却中断的请求由原任务显式恢复，不创建第二份执行；远端提交结果不明继续按既有检查点处理，不盲目重交。
- 停止或重开保留记录但关闭自动消费，只有明确恢复后再处理。内部每批工具决策结束不视为父任务完成，也不触发后续要求。

这使用现有文件与少量分支完成，不增加常驻队列调度器或通用状态机。

### 4. 从画布选中项生成固定引用，第一版不建设搜索系统

输入框提供“加入选中项”，标签可移除，并以简短用途区分“目标／参考”。普通选择仍是默认目标线索；显式目标优先，多个对象关系不清时询问，而不自动修改全部。历史产物通过现有产物详情加入，第一版无需全局 `@` 搜索。

每条引用包含：稳定引用 ID、用途、项目内来源、页面／运行、节点业务身份、媒体或结构化数据类型、产物相对路径、版本或签名，以及供 UI 显示的短标签。未生成节点只能提供对象引用，不生成虚假文件路径；漫画原页、单格来源仍可引用。

后端根据真实运行产物解析并复核，前端标签和路径不是可信事实。发送和消费时校验路径范围、类型、可读性及签名；跨页只读参考允许在同一项目内使用，修改目标仍受任务范围限制。现有运行能保留版本就引用原版本，内容被覆盖则明确失效，不静默替换、不复制整套版本仓库。

消息只保存引用与必要摘要，不内嵌图像或视频二进制。点击引用优先复用现有画布定位回执；旧运行未投影到当前画布时查看原产物，不把同名新节点当作定位成功。引用资料不提升模型或文件权限。

这一方式先解决准确指代，比同时建设素材库和全量搜索更小且易于验证。

### 5. 让引用进入真实专业输入与缓存签名

在现有 `agent/tools.py` 到规划／生成入口之间传递任务书和引用清单，按阶段整理实际输入：

- 来源文本、镜头结构和用户要求作为明确来源的文本资料。
- 图像参考按现有客户端多模态输入／参考图接口携带，保留漫画原图与前序必要参考；不以标签或路径字符串代替图片。
- Reviewer 获得本次目标、参考用途、原作约束及实际候选，能检查是否偏离要求。
- 视频／音频等不被当前任务接纳的控制条件明确阻塞或询问用途；视频审查若支持读取则仅在该用途使用，不推断 H3 生成同样支持。

将有效引用签名与用途计入相关产物的现有输入签名；变化时通过显式新任务／修订运行生成新结果，不复用未含参考的缓存。对旧运行只读，不扩展全局依赖图或自动失效传播。不得仅改变缓存元数据却复用旧结果。

### 6. 用精简任务书和回报连接已有专业阶段

在现有 schema 中定义可序列化的任务书与回报，保存在原阶段子任务中；若实现需要拆分，只增加一个直接职责模块，不建立 Agent 基类或注册系统。

| 专业任务书 | 专业回报 |
| --- | --- |
| 父任务／来源请求、阶段、目标与预期输出 | 对应任务、实际结果状态与短摘要 |
| 原漫画、规划输入及版本引用 | 真实产物与审查文件引用、是否复用 |
| 可修改对象／范围与只读参考 | Reviewer 原结论、问题位置、依据与修订事项 |
| 必须保留的事件、对白、配色及既定约束 | 阻塞或需要上游处理的原因与目标 |
| 本次授权范围 | 建议接收者及下一步，明确仅为建议 |

任务书由总 Agent 的结构化委派结果和已验证上下文构成，后端强制限制真实范围。专业 Creator／Reviewer 继续用原阶段提示词，仅注入相关任务要求与引用，不需要读取整段聊天，也不新增子会话树。回报优先从已落盘产物和现有审查结果归一化得到，不为了生成一段回报额外调用模型。

`stage_tool()` 记录委派与返回，`professional_call()` 保留真实调用边界，必要反馈事件由原流水线在实际交接处发出并关联问题／轮次。总 Agent 接到“需上游处理”回报后通过现有有界工具协调；阶段内 Reviewer→Creator 的确定性重试标为“流程交接”，不伪造成总 Agent 又做了一次模型决策。总 Agent 无权修改拒绝结论，业务轮次和现有状态转换保持不变。

### 7. 时间线展示交接结果，详细依据按需展开

- 用户消息显示引用标签、送达方式和实际处理状态，不再一律显示“待修改”。回答关联原消息，后续任务卡关联其来源请求。
- 专业卡片保留当前角色／状态和一行摘要；展开显示任务书、真实提交、审查问题、反馈接收者及版本产物。
- 沿用已有任务和画布双向定位、折叠展开与完成回执。没有新调用、只复用旧结果时显示“复用”，旧记录没有任务书就显示历史资料，不补造角色协作。
- 不展示内部完整提示词、模型思考或大量技术日志。分格、下载、剪辑继续以工具名称展示。

## Risks / Trade-offs

- 自然语言有歧义 → 总 Agent 结构化理解，目标不明明确询问；不用默认编排和静默扩大范围兜底。
- 长调用期间一般问题的回答可能延后 → 进度和停止走本地即时通道，其余显示“当前步骤结束后处理”；不引入并发制作。
- 引用文件可能被覆盖 → 固定真实版本和签名，执行前复核；缺失即明确失效，不建设完整快照系统。
- 两个进程更新会话造成覆盖 → 短锁只写独立收件文件，活动引擎统一接回会话，时间线按 ID 合并。
- 同时收到修改与停止 → 停止标识优先检查，认领不等于完成，恢复前不继续生产；已有远端任务身份保留。
- 增加上下文抬高调用成本 → 仅传相关任务和选定参考，回报由真实文件整理，不增加报告模型或所有历史媒体。
- 任务书看起来比实际执行更完整 → 后端校验和实际输入记录为准；拒绝、不支持、复用均如实报告，不能用文案代替执行。

## Migration Plan

1. 先扩展可选字段和只读兼容，旧会话／任务／待修改记录继续可查看与显式恢复，原阶段按钮不变。
2. 接入统一消息收件、边界消费与独立后续任务，保留原内容修改执行路径；再接入固定引用与专业任务书／回报。
3. 完成输入区和时间线展示，使用一个本地项目做原生客户端走查，确认问答、修改、排队、停止、版本引用和真实交接。
4. 少量针对消息归属与引用映射的检查，加现有关键检查和桌面构建；不新增大规模 Mock。模拟协作明确标注，不能作为付费模型效果证据；默认不启动新付费生成。
5. 实施时更新创作 Agent 使用说明、固定参考记录与验收说明。回退时先停止活动任务、保存项目副本并撤回代码改动；旧客户端不能消费新消息类型，存在新版待处理请求的项目不交给旧客户端继续制作，不执行破坏性数据降级。
