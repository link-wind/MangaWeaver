## Purpose

让用户在制作期间能够询问进度、补充当前要求和安排后续工作，并明确看到消息实际交给了哪个任务。送达方式与内容意图分别处理，避免普通问答误触发修订，同时保留既有授权、检查点、停止和显式恢复约束。

## ADDED Requirements

### Requirement: 区分送达方式与消息意图
系统 MUST 区分“调整当前任务”和“稍后处理”两种送达方式，并分别判断消息属于问答、内容修改、制作请求或执行控制。运行中 MUST 不再将所有消息直接视为内容修改，也 MUST 不因未选择节点而默认修改镜头编排。输入区 MUST 以简洁的单一送达选择展示本次方式。

#### Scenario: 制作期间询问进度
- **WHEN** 用户在当前任务运行时询问“现在做到哪了”
- **THEN** 系统根据真实任务快照回答，保持原目标和执行状态，不新建修订运行或生产调用

#### Scenario: 无选中目标的含糊修改
- **WHEN** 用户发送“改一下这里”，消息及固定上下文不足以确定修改对象
- **THEN** 系统询问目标并保留原任务，不默认修改编排或全部镜头

### Requirement: 消息归属在发送时固定
系统 MUST 在接收时为消息保存稳定身份、送达方式、原文、时间、所属项目、页面、运行基线、当前任务关联、目标引用及授权快照。切页、换选中对象或刷新 MUST 不改变已发送消息归属。后续要求 MUST 保留独立身份，不覆盖当前任务目标。

#### Scenario: 后续要求与当前任务分开
- **WHEN** 用户在第十二页制作期间选择“稍后处理”并要求完成后规划第十三页
- **THEN** 系统保存独立后续要求及第十三页目标，当前第十二页任务继续保持原目标

### Requirement: 在安全边界处理当前任务补充
当前任务补充 MUST 在正在执行的模型调用返回、真实结果与检查点保存后、下一项受影响工作启动前处理。系统 MUST 串行接收和处理，不并行启动第二套制作。普通问题回答后 MUST 保留原制作进度；只有明确内容修改才进入原有修订与审查路径，影响已完成内容时 MUST 明确实际修订范围，不宣称撤回已发生的生成或计费。

#### Scenario: 生图期间修改第二镜头
- **WHEN** 第一张图正在生成，用户要求缩短第二镜头停顿
- **THEN** 当前调用先落盘，消息显示待处理，随后针对固定对象处理修订；已提交生成结果保留，不将消息显示为立即生效

#### Scenario: 普通知识问题
- **WHEN** 用户在运行中询问需要模型解释的问题
- **THEN** 系统在安全边界以只读问答处理并继续原目标，不因回答把制作任务标为完成或擅自启动修改

### Requirement: 后续要求的执行边界
“稍后处理”请求 MUST 在当前任务正常完成后按接收顺序处理，只有仍在活动客户端、未停止、目标清晰且已获对应范围授权时才可启动。需要新页面、输入或额外生成范围但未获明确授权时 MUST 等待用户决定；排队行为本身 MUST 不视为无限制作授权。当前任务失败、阻塞、暂停或停止时 MUST 保留后续要求，不自动绕过当前问题执行。

#### Scenario: 已授权的后续规划
- **WHEN** 用户明确要求完成第十二页编排后规划第十三页，并允许这两项规划，当前任务正常完成
- **THEN** 活动客户端按独立任务启动第十三页规划并保留原任务记录，不要求重复授权、不隐式开始生图

#### Scenario: 当前任务失败
- **WHEN** 当前任务执行失败且后续要求仍在排队
- **THEN** 后续要求保持待处理，界面展示当前失败与可用恢复操作，不将排队任务自动当作恢复方案

### Requirement: 停止优先于排队执行
停止按钮及明确的停止指令 MUST 进入现有本地中断流程，阻止后续阶段、批次和待处理请求自动启动，不能仅保存为内容修改。停止 MUST 保留已完成产物和请求记录，并说明本地停止不等于取消远端任务。重开项目 MUST 只恢复显示，恢复执行须有明确用户动作。

#### Scenario: 停止后仍有消息
- **WHEN** 用户停止运行并重开项目，尚有当前任务补充和后续要求
- **THEN** 系统显示中断及待处理记录，不自动消费任何请求，不重复提交已存在的远端视频任务

### Requirement: 收件与处理结果真实可见
消息 MUST 展示待处理、已接收、已回答、已应用、已撤回或需决定等与真实处理一致的结果，并关联实际任务。尚未接收的请求 MUST 支持撤回。重复刷新或重复递送同一请求 MUST 不产生重复修订、后续任务或付费提交。旧待修改记录 MUST 保留原本语义并可查看，不在打开项目时重新分类或执行。

#### Scenario: 撤回后续要求
- **WHEN** 用户在后续要求被接收前撤回它
- **THEN** 记录保留已撤回结果，当前任务不受影响，该要求不会再启动

#### Scenario: 重复递送
- **WHEN** 同一已接收消息因客户端重连被再次提交处理
- **THEN** 系统返回原归属与处理进度，不创建第二个修订或后续任务
