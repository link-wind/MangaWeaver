# MangaWeaver 技术架构草案 v0.1

> 日期：2026-10-23  
> 状态：供用户评审，以下默认值是本轮提案，不代表已获确认或已实现。  
> 当前基准：保留三阶段结构；增加镜头编排层；静态镜头沿用首帧路线，动作镜头暂用首尾帧分段生成。本文替代早期图中的一格一镜头、统一视频生成路线等假设。

> 核心实施原则：大部分细节参考 Manga2Animate，围绕已确定的差异做增量修改，见根目录 [AGENTS.md](../AGENTS.md)。本文未确认的默认数值和工程细节不构成另行重写参考机制的要求。

> 实施规模约束：优先主路径，不设计过多回退逻辑和测试。保留业务反馈循环及必要恢复；错误清晰暴露，验证以小样例和关键接口为主。

## 1. 方案总览

核心任务是把漫画中的关键瞬间组织成有节奏的动画镜头。动作细节、模型运动平滑度和首尾接缝是支撑问题，不替代镜头编排目标。

| 阶段 | 内容 | 相对参考项目的变化 |
| --- | --- | --- |
| 一：预处理 | 有序漫画格、OCR、角色描述 | 沿用；允许人工修正或提供已有预处理结果 |
| 二：脚本、镜头编排与视觉规划 | 原作理解、分类与镜头编排、动作镜头演出、分镜制作及反馈 | 主要改进部分 |
| 三：视频生成与剪辑 | 静态首帧生成、动作首尾帧分段生成、候选审查、连接与导出 | 保留候选选择思路，扩展任务接口及连接逻辑 |

运行形态：本地 Python CLI、结构化 JSON、本地素材目录；新增 Electron + React 桌面工作台，通过受限 IPC / JSONL 子进程复用原有引擎，使用说明见 `docs/DESKTOP.md`。调度由程序完成，Agent 通过专用任务、上下文、输出协议与反馈协作。第一版不引入全局自主导演、不搭建 Web 服务。

## 2. 分类规则

### 2.1 分类的是呈现需求

类别只保留 `static` 与 `action`，避免增加模糊的第三条生成路线。分类依据是镜头是否需要展示主要事件的时间过程，不是人物有没有动。

| 类别 | 判断标准 | 示例 | 生成方式 |
| --- | --- | --- | --- |
| static | 单个构图和关键状态足以表达意图，不需要控制多个主要状态之间的变化 | 对话、反应特写、场景交代、有意停留 | 单张分镜首帧生成；允许局部运动与轻微运镜 |
| action | 表达依赖主要状态的变化及其先后，需要控制漫画关键瞬间的位置或前后过程 | 攻击及受击、拿取物体、跨格连续动作、由静转动的重要事件 | 关键帧序列，相邻帧作为首尾条件分段生成 |

对话不是必然静态，反应也不是必然静态：若表达重点是缓慢认出对方、逐渐惊恐等变化，应走动作路线。单格漫画也可以判为动作，多格漫画也可以编成静态镜头。

### 2.2 分类发生两次，但只有一个编排层

镜头编排 Creator 先结合上下文识别事件单元，再生成输出镜头，并给每个输出镜头标注最终类型。源漫画格可记录初步判断，但不直接锁定生成路线。

遇到静态与动作混合内容，优先按表达目的划分镜头；不能只为满足分类机械增加切镜。无法确定时输出证据、疑问及建议，由编排 Reviewer 判断；仍有关键歧义则交给人工。

## 3. 镜头编排权限与上下文

### 3.1 第一版输入范围

- 每次由用户指定一个场景或连续叙事片段，建议 4～8 格漫画。
- 可以横跨页面，但不跨明显的时间跳跃、场景切换；边界由用户初步确认。
- 可附前后各一格作为只读上下文，不自动加入输出范围。
- 第一版不自动做整章场景划分。

### 3.2 允许的改编

- 合并多个漫画格，形成一个连续动画镜头。
- 将一格中的多个表达目的拆成多个镜头。
- 调整景别、机位和镜头入点、出点。
- 有依据地补充过渡、反应或空间交代镜头。
- 用动作中的关键瞬间承载原漫画画面，而不默认放在首帧。

### 3.3 必须保持的约束

- 保持原作的关键事件、因果顺序、人物身份、关系、动作结果和对白归属；首版不重新排列故事事件。
- 不新增决定剧情走向的行动，不凭空增加主要人物、地点或对白。
- 机位改变时保留场景中的人物与物体关系；区别屏幕左右与场景空间左右，不能因机位变化直接判定空间错误。
- 每个输出镜头记录来源和编排理由；新增镜头必须关联其支持的原作事件。
- 每个源格标注已覆盖、合并覆盖或申请省略。关键事件不可省略；首版省略原格需人工确认。

为了限制试验规模，每个案例默认不超过 6 个输出镜头、8 个视频生成段；超出时返回简化建议或转人工调整，不能无记录地丢弃内容。

## 4. 第二阶段的 Agent 分工

| Agent | 输入与输出 | 边界 |
| --- | --- | --- |
| Script Creator | 从原作、OCR与角色描述生成逐格来源脚本 | 先准确理解原作，保留来源 ID，不负责最终镜头数量 |
| Character Reviewer / Clip Reviewer | 检查角色与逐格描述，组合来源脚本并给反馈 | 审查原作事实，不用静态布局标准否定后续授权的改编 |
| Shot Arrangement Creator（镜头编排） | 来源脚本＋原漫画 → 事件分组、分类、有序镜头清单、总节奏 | 决定有哪些镜头及其关系 |
| Shot Arrangement Reviewer | 对照原作，检查覆盖、合并拆分、类型、切镜与整体节奏 | 完整场景方案整体选择，不任意拼接不同候选的局部镜头 |
| Shot Direction Creator（镜头演出） | 对动作镜头设计入点、关键瞬间位置、强调、停顿、出点与锚点 | 不以逐关节运动或固定动作模板为核心；静态镜头不经过该生成步骤 |
| Shot Direction Reviewer | 检查动作镜头内部节奏、锚点必要性及跨段可实现性 | 若需要改变镜头数量或切镜结构，反馈编排层 |
| Storyboard Creator | 静态：一张分镜；动作：按锚点制作关键画面 | 依照选定设计作画；不自行改变时间结构 |
| Storyboard Reviewer | 检查人物、风格、空间、指定时间角色及关键画面之间的一致性 | 不能只凭几张图判定实际运动已经自然 |

复用参考项目的 Creator／Reviewer 配对及结构化反馈机制，不增加自由协商的全局 Director。原作图像必须能被对应 Reviewer 读取，而不是只审查模型自己写的文本。

## 5. 最小数据协议

正式数据模型后续实现；以下为首版必须表达的内容。

| 产物 | 必要内容 |
| --- | --- |
| SourceScript | 场景 ID、漫画格 ID、角色、事件、对白、可见事实、推断与疑问 |
| ShotList | 有序镜头 ID、来源格、事件 ID、static/action、分类与编排理由、景别和机位、表达目的、目标时长、与下一镜头的关系 |
| DirectionPlan | 动作镜头的入点、出点、呈现节拍、原漫画关键瞬间、锚点序列及目标时间 |
| VisualAssets | 关键帧 ID、所属镜头、时间角色、图像路径、来源／推断、生成版本、评审状态 |
| GenerationPlan | 模式、首帧／尾帧引用、请求时长、镜头提示、计划与素材版本 |
| ReviewReport | 候选选择、是否可采用、阻断问题、证据、修订对象与范围、未能确认的内容 |

源格、输出镜头、关键帧、生成段必须使用不同 ID。同一镜头可引用多个源格；同一源格也可支持多个输出镜头。参考项目中以漫画格编号直接代替生成片段编号的假设需要解除。

镜头间第一版只支持 `cut`；同一镜头内分段连接使用 `continuous`。不引入自动叠化等额外转场。连续性检查要求动作意图可理解，不要求不同机位的画面构图相同。

## 6. 关键帧与节奏设计

### 6.1 动作镜头默认策略

- 默认先提出 2～3 个锚点：入点、必要的原漫画关键瞬间、出点。
- 原漫画可对应其中任意位置；若本来就是合适的入点或出点，不额外补一个同义锚点。
- 多个漫画格共同描述连续事件时，按必要性保留多个原作锚点；每个动作镜头首版最多 4 个。
- 关键帧可根据漫画重绘，以统一画幅、人物、背景和视角；“保持原作依据”不等于直接使用带对话框的漫画裁图。
- 仅需要解释、没有视觉证据的内容必须标记为推断。
- 锚点连接要求处于可连续表达的空间和机位；若实际需要切镜，应返回编排层拆成不同镜头，不能强制插值。

### 6.2 时间分配

编排层分配整场戏的镜头时长；演出层在动作镜头内部确定锚点时间和节拍。使用秒数，导出时再对齐输出帧率。

首版规模以小场景验证为主。实际接入核实后，MiniMax H3 每个生成段必须是 4～15 整数秒；静态镜头同样遵守该约束，动作镜头总时长由相邻关键帧段累加。此前静态 2～4 秒的试验设想不作为当前可执行时长。

区分目标时长、API 请求时长和成片实际时长。若所需间隔小于接口最短时长，不静默拉长动作：先尝试减少非必要锚点或调整编排，无法兼顾时标记当前后端不适配并转人工。第一版不以统一加速、补帧或叠化掩盖节奏及接缝问题。

首尾帧只能间接安排关键瞬间位置，不能保证段内速度曲线或精确停顿。评审需要比较目标与实测差异。

## 7. 第三阶段：当前接续路线

### 7.1 静态镜头

沿用参考项目逐镜头首帧方式：一张分镜＋镜头描述生成候选。允许适度局部运动和运镜，提示避免不必要动作与模型自行切镜。

### 7.2 动作镜头

计划对关键帧 K0、K1、K2，构建 K0→K1 和 K1→K2 两个独立的首尾帧生成任务。视频后端选用 MiniMax H3，具体接入方式及首尾帧条件能力需验证；本节是目标执行路线，不表示已确认该模型接口能够执行。当前不使用历史视频续写，不实现 latent prefix，不要求支持任意时间位置关键帧的专用模型。

各生成段输出后，先审查是否遵循端点、是否出现意外切镜，再组合完整镜头检查节奏和接缝。共享输入关键帧不保证实际输出端点完全相同，也不保证速度连续；记录接缝前后帧的实际差异。

只对确认重复的边界帧做去重，不无条件删帧，不默认交叉淡化。若实际端点偏离、镜头运动或速度明显跳变，判定为问题，不把拼接完成当作接续成功。

### 7.3 输出与声音

当前实现成片统一为 16:9、720P、24 fps，与 H3 的 24 fps 输出保持一致；在最后组装时做规格归一化，保留原始视频。帧率转换不等于运动修复。

默认输出彩色动画、日语配音与中文字幕，保留并拼接原生音轨。视频提交前，Gemini Creator／Reviewer 完成原作中文对白的日语翻译、说话人及分段时间安排，H3 只演绎已确认台词、环境声与动作音效，不逐段生成背景音乐。视频评审检查实际声音与画面同步、重复对白和声音接缝，实际发声时间用于后期字幕；保留无字幕有声版及 SRT。独立 TTS、固定声线克隆及连续配乐暂不建设。

## 8. 反馈循环与依赖管理

| 问题 | 回到哪里 |
| --- | --- |
| 原作理解、人物、对白错误 | Script Creator |
| 分类、事件合并拆分、镜头关系或整体节奏错误 | Shot Arrangement Creator |
| 镜头入点、原作瞬间位置、强调、出点错误 | Shot Direction Creator；静态镜头则回编排层 |
| 画面未实现既定计划、人物或背景漂移 | Storyboard Creator |
| 视频端点、段内生成或接缝问题 | 第三阶段候选选择；有限追加生成后转人工 |

第二阶段按顺序执行各组 Creator／Reviewer，汇总反馈后进行下一轮定向修订；保留未受影响的产物。审查结果区分“候选中更好”和“已经可采用”，允许所有候选均不合格。

第一版不做第三阶段视频审查自动驱动整套上游重规划的大循环。人工可根据报告回改，之后恢复受影响任务。

产物记录对应的输入配置和运行版本，不能把最新脚本、旧演出方案和旧图随意混用。首版通过独立运行目录及显式指定重跑阶段保证对应关系；上游变化时明确重跑相关下游，不提前实现通用依赖图或自动失效传播系统。

## 9. 候选、迭代与预算默认值

| 环节 | 首版默认 |
| --- | --- |
| 来源脚本 | 2 份候选，保留原项目的组合选择思路 |
| 场景镜头编排 | 2 份完整候选，整份选择并检查原作覆盖 |
| 每个动作镜头的演出 | 2 份完整候选，整体选择 |
| 静态分镜或单个关键帧 | 2 个候选，先检查再结合相邻锚点审查一致性 |
| 第二阶段循环 | 最多 2 轮：初始生成＋一轮针对性修订 |
| 每个视频生成段 | 初始 2 个候选；无可用结果时最多追加 1 个 |
| 单案例视频上限 | 16 次新提交，累计请求生成时长上限 90 秒，先达到者停止 |

所有上限可配置，超过时保留结果、失败记录与未完成任务。90 秒是请求时长计数，不是费用估算；实际费用按供应商账单／用量记录。

网络读取与查询可有限重试；提交请求结果不明时先恢复／查询任务，不自动重新提交付费生成。第一轮小样例的编排与关键画面先由人工查看，再进入视频试验。

## 10. 模型与工具默认路线

- 文本、多模态理解与审查：先沿用参考项目的 Gemini 接入方式，模型 ID 外置配置，不把仓库动态默认值当作已验证可用的账号能力。
- 分镜与关键画面：先沿用参考项目的 Gemini 图像生成接入，保持同一场景的模型与风格配置一致。
- 视频：选用 MiniMax H3 作为第一版后端。优先验证同一模型对静态与动作路线的支持，减少混用模型造成的对照干扰；具体 API／部署入口、模型 ID 和输入映射在接入验证后确定。
- 整段分镜参考路线仅保留为对照，不承担首版静态／动作混合工作流。
- 本地素材处理、抽帧、剪辑与导出使用 Pillow／FFmpeg；不引入本地视频模型训练与部署。

MiniMax H3 的首帧、首尾帧或其他参考条件、时长范围、时长粒度与账号权限需根据实际接入入口核实，不沿用其他后端的参数与能力假设。如果所选入口不支持首尾帧，先记录能力缺口并讨论适配方式，不自动更换后端或把参考图输入当作首尾帧控制。预检应在创建付费任务前完成。

仍需要外部条件才能确认的只有：可用账号与模型权限、实际预算、接口端点遵循程度及生成效果。当前不申请凭据、不运行付费生成。

## 11. 首轮验证与通过标准

先准备 6 个固定短案例：纯静态对话／反应、单格高潮、跨格连续动作、静态与动作交替、动作后反应镜头、相似姿态但实际应切镜的场景。素材由用户提供或使用允许实验的素材。

分两步验证，避免一开始运行所有案例：

1. 先验证“单格关键瞬间位于中段”和“跨格动作＋反应”两个案例，打通分类、编排、关键帧与接续。
2. 核心路线可用后再扩展到 6 个案例及对照实验。

对照设置：

- A：参考项目逐格首帧路线。
- B：使用我们的镜头清单，但每个动作镜头仍只使用入点首帧生成。
- C：相同镜头清单，动作镜头改用首尾帧分段，静态路线不变。

A 与 B 用于观察镜头编排影响；B 与 C 用于观察生成条件影响。尽量保持视频模型、素材和总成片时长一致；候选次数、请求生成总时长、图像成本及总耗时均单独记录。不把额外预算带来的收益直接归因于架构。

先将原作覆盖、数据映射有效、无阻断性设计问题作为进入生成的门槛。视频以匿名打乱顺序的人工对照为主，分别评价镜头节奏、原作瞬间位置、静态／动作切换、接缝及原作忠实度；自动 Reviewer 辅助定位，不作为唯一成功依据。小样例结果只用于判断可行性，不作统计显著性或普遍优越性声明。

### 职责与调用约定

- `cli.py` 仅负责参数与阶段入口调用，不包含镜头编排或视频生成业务逻辑。保留三阶段可独立执行的能力，不再为旧脚本额外建设兼容入口。
- `config.py` 统一读取环境变量、模型配置和运行路径，显式传给阶段函数；不引入配置中心或多层配置系统。
- `schemas.py` 维护来源格、镜头、锚点、生成任务和评审结果的跨阶段协议；仅做必要校验，不建设通用实体框架。
- `planning/pipeline.py` 调度来源脚本、镜头编排、动作镜头演出和视觉分镜的 Creator／Reviewer 循环。各角色在对应模块中实现，不额外建立 `agents/` 类体系。
- `generation/pipeline.py` 组织候选生成与选择；`tasks.py` 构建静态首帧和动作首尾帧任务；`video_review.py` 负责评审；`assembly.py` 负责连接、剪辑和导出。
- `clients/gemini.py`、`clients/minimax.py` 直接封装所需的请求、异步查询和响应处理；沿用参考项目的有效实现，不建立插件注册表、通用客户端基类或多层适配链。
- `io.py` 只保留实际复用的文件读写函数；原有日志、运行记录及统计按需要迁入对应职责位置，不为维持旧文件数量额外创建模块。
- 提示词以所选职责目录组织，尽量复用参考内容，仅修改镜头编排、分类、演出与首尾帧方案需要调整的部分。视频生成和评审模板在实现时归入对应职责目录，不另建模板引擎。
- `examples/` 存放小规模输入案例及运行说明；用户实际输入路径通过配置指定，不再要求固定的 `target/` 根目录。

## 15. 视频型号更新

用户后续确定：所有后续视频生成使用 `MiniMax-H3-Lite`、默认 `480P`。Lite 支持 4～15 整数秒与首尾帧输入；不支持 2K。已完成的标准 H3 单段测试保留原始记录，Lite 尚待真实生成验证。统一 720P 导出只调整文件规格，不提升原生 480P 的实际细节。
